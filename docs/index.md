# LumaTrack provider

Records automation run events in [LumaTrack](https://lumatrack.io/?utm_source=terraform-provider),
which prices what each run saved against the manual baseline you defined. One
`lumatrack_run` resource in your config turns an apply into measured evidence.

The provider deliberately exposes one resource. Creating automations and reading
value numbers both need a full-access key, and a pipeline that only reports runs
should be able to hold an ingest-only key that cannot read your ledger back.

## Example usage

```terraform
terraform {
  required_providers {
    lumatrack = {
      source  = "LumaTrack/lumatrack"
      version = "~> 0.1"
    }
  }
}

provider "lumatrack" {
  endpoint = "https://lumatrack.io"
  api_key  = var.lumatrack_api_key
}

resource "lumatrack_run" "network_baseline" {
  automation       = "network-device-baseline"
  status           = "success"
  duration_seconds = 142
  units            = 240
}
```

## Authentication

Create the key in LumaTrack under Settings, API keys. It's shown once, and only a
hash is stored. Keys come in two scopes, and an **ingest-only** key is enough for
this provider. Deploy that one: if it leaks, an attacker can post junk runs, and
they cannot read or restate your ledger.

Both arguments fall back to the environment, so no key has to sit in a `.tf`
file or a state-visible variable:

```sh
export LUMATRACK_ENDPOINT="https://lumatrack.io"
export LUMATRACK_API_KEY="lmt_..."
```

A value set in the provider block wins over the environment.

## Rate limits

Requests are counted per organization across all of its keys. A 429 that carries
`Retry-After` is a rate limit against a fixed one-minute window, so the provider
waits and retries once. A monthly event-cap 429 carries no `Retry-After`; that
one fails the apply with the server's message, because retrying against a
ceiling that won't move today would just burn the window.
