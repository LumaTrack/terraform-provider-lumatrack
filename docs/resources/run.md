# lumatrack_run (Resource)

Reports one automation run event to the LumaTrack value ledger when applied.

A run is an immutable fact, and the resource behaves like one. Changing any
attribute replaces it and records a second run. Destroying it drops it from
Terraform state and leaves the recorded evidence in LumaTrack, because the run
happened. Refresh reads nothing back, since an ingest-only key acknowledges a
replay rather than echoing stored evidence.

## Example usage

```terraform
resource "lumatrack_run" "network_baseline" {
  automation       = "network-device-baseline"
  status           = "success"
  duration_seconds = 142
  units            = 240

  metadata = {
    workspace = terraform.workspace
    commit    = var.git_sha
  }
}
```

### Reporting failures

Failed runs cost money and save nothing, so report them. A resource inside a
failed apply never gets created, which means the status has to come from your
pipeline rather than from Terraform:

```terraform
variable "run_status" {
  type    = string
  default = "success"
}

resource "lumatrack_run" "network_baseline" {
  automation     = "network-device-baseline"
  status         = var.run_status
  failure_reason = var.run_reason
  external_id    = var.pipeline_run_id
}
```

Apply the real work first, then apply this resource with `run_status` set from
the exit code. On HCP Terraform, a run task sees the outcome directly and is the
better fit.

### One run with units, rather than many runs

If an apply baselines 240 devices, report one run with `units = 240`. The ledger
prices that as fixed setup plus marginal minutes per device, which is the number
that survives a CFO's review. Two hundred and forty separate resources would
each consume an event against your plan's monthly cap and say the same thing.

## Idempotency

Leave `external_id` unset and the provider generates one and keeps it in state,
so re-applying unchanged config records nothing new. That guarantee lives in the
state file. Set `external_id` to your pipeline's own run id when you want
exactly-once reporting that survives a lost state file:

```terraform
external_id = "gitlab-${var.ci_pipeline_id}-${var.ci_job_id}"
```

## Schema

### Required

- `automation` (String) Slug of the automation this run reports as. List them with `GET /api/v1/automations`, or create them in the app.

### Optional

- `duration_seconds` (Number) Wall-clock runtime in seconds. Omit it rather than sending a guess.
- `executed_at` (String) ISO 8601 timestamp, for evidence that genuinely happened earlier. Omit it for live events. Closed months are refused.
- `external_id` (String) Your system's run id, which makes ingestion idempotent. When you leave it unset the provider generates one and keeps it in state, so re-applying unchanged config records nothing new. Set it to your pipeline's own run id when you want exactly-once reporting to survive a lost state file.
- `failure_reason` (String) Root cause for a failed run, e.g. `auth/credential`. Powers the failure-reason Pareto on the automation page.
- `metadata` (Map of String) String key/value pairs kept with the run.
- `source` (String) Reporting system stored on the run. Defaults to `terraform`; override it to tell environments or pipelines apart.
- `status` (String) One of `success`, `failure`, `skipped`, `cancelled`. Defaults to `success`. Report failures too: they cost money and save nothing, and the ledger prices that honestly.
- `units` (Number) Records or items this run processed. Multiplies value when the automation is valued per unit. The server defaults to 1 when omitted.

### Read-Only

- `deduplicated` (Boolean) True when this `external_id` had already been recorded, so the request was an idempotent replay rather than a new run.
- `held` (Boolean) True when the run was stored but held over the plan's monthly event cap. Held runs are excluded from every value number until the plan is raised.
- `id` (String) The LumaTrack run id (`run_...`).

## Import

Runs can't be imported. A run is evidence LumaTrack already holds, and an
ingest-only key cannot read it back, so there's nothing for Terraform to adopt.
